# Step 7 — Adversarial review

7. **Adversarial review.** Never deliver without this pass — a mechanical PASS is not a review. Run [`references/reviews.md`](../reviews.md): 3 core reviewers plus one per target market segment (recruiter 30-second scan, hiring manager of the field, ATS expert, plus one per segment with an invented but realistic posting) — the market-segment reviewers are part of this FIRST pass, not an optional later round. Spawn every reviewer on the cheapest model your runtime offers — a fan-out inheriting an expensive main-loop model burns budget fast. When the runtime has sub-agents, spawn one sub-agent per reviewer persona; never merge personas into one agent. If your runtime has no subagents, run the personas one at a time in the main session, clearing between them: the review is mandatory, the parallelism is not. **Compact path** (only when the runtime has no sub-agent tool, declared as `runtime: none` in `review.md`): skip the full panel; run, sequentially in ONE pass yourself, only the ATS/fact-diff check and the hiring-manager read from `references/reviews.md`, each ≤5 findings; fix, then re-run step 6. A runtime with sub-agents never takes it, whatever the budget or model. Give them rendered PNGs *and* sources. `Layout review: self` is valid only when the runtime has no sub-agent tool. The layout reviewer (after any redesign; always on the full path) runs the look-checklist routes of step 6 and the report carries exactly one line `Layout review: self | subagent <model> | user` — absent, `skipped` or reviewed from source alone = step 7 not done; with no redesign and the compact path, write `Layout review: not run (no redesign)`. The final verify prints that line under its PASS, derived from `layout:` in `review.md`: paste it with the output, do not retype it; the report's line is that one (the gate cannot check the value itself, e.g. that no redesign happened: it is your declaration). Redesign = a new template or family was chosen, or layout parameters (margins, sizes, spacing, section order, header) were changed in this session; reusing the user's existing approved design unchanged is not one, and a first build from `pick_design.py` always counts as a redesign. The layout reviewer's report line is `Layout review: …`. Step 6's `Visual pass:` line does not replace it. Apply findings per the synthesis rules in `reviews.md` (a fact-diff finding is applied, the rest are cross-examined); findings demanding invented facts become questions for the user. After applying findings, go back through step 6 before delivering; if applying layout findings changed the page, re-run the layout reviewer on the new render before reporting the `Layout review:` line.

**Review record.** Write `review.md` beside the CV `.typ`, last: after the final re-run of step 6, because the final verify FAILs without it (missing, older than the `.typ`, or incomplete). Format:

```
runtime: sub-agents | none
cv: <every .typ basename this record covers, comma-separated>
personas: recruiter, hiring manager, ATS, <market-segment personas…>
layout: subagent <model> | self | user | not run (no redesign)
## Findings
- <persona>: <finding> → applied
- <persona>: <finding> → rejected: <reason>
```

One record covers the CVs it lists on `cv:`; the gate FAILs when the CV being verified (every CV, under `--all DIR`) is not listed, and when the record is older than the `.typ` (for an academic CV, also older than its `data.toml`). `runtime: sub-agents` needs recruiter, hiring manager and ATS as persona names that *start with* those words (`Recruiter (30-second scan)`, `Hiring manager of the field`, `ATS / parsing expert`; after `ATS` only `expert`, `parsing`, `check`, `reviewer`, `fact`, `diff` are read; `fact diff` is accepted as a stem too (`fact-diff reviewer`, `fact-diff check`)) and are not segment names — anything containing `segment` (`nurse-recruiter segment`) or another stem (`ATS-savvy startup`) does not count — and a `layout:` of `subagent <model>` or `user` (`self` and `not run (no redesign)` belong to `runtime: none`; the whole documented form is required, `subagent` alone FAILs); `runtime: none` (compact path) needs ATS or fact-diff, and hiring manager. **Academic mode** (`verify_academic.py`) swaps the core personas: `sub-agents` needs committee member, extraction-and-counts auditor (name starts with `extraction`) and department head; `none` needs the extraction auditor and the department head (the fact diff). Every finding ends `→ applied` (a trailing note starting with punctuation is fine: `→ applied (bullet 3)`; the resolution is the last `→`/`->` of the bullet, and a further arrow after it makes the bullet unresolved) or `→ rejected: <reason>` (`->` also read); an unresolved bullet FAILs. Leftover layout FAIL items are findings too, resolved the same way. Findings are the `-`/`*`/`1.`/`1)` bullets under `## Findings` (any text after the heading is fine; indented lines continue the bullet, bullets nested under a finding belong to it, an indented bullet with no finding above it is a finding); text under the heading with no parseable finding FAILs. After any later edit of the `.typ`, update `review.md` and re-run step 6; your own final verify never uses `--rebuild` (that flag is for the candidate's `rebuild.py` only).
